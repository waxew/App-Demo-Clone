# فاز ۱ — تثبیت هسته و ایمنی داده

وضعیت: شروع‌شده

هدف این فاز، ثبت قرارداد فعلی برنامه قبل از هر refactor بزرگ است تا داده‌های موجود، فاکتور و قابلیت‌های native آسیب نبینند.

## محدودهٔ فاز

- استخراج مدل state و مسیرهای تغییر آن
- فهرست‌کردن کلیدهای storage
- استخراج قرارداد Native Bridge
- ثبت ترتیب بارگذاری scriptها
- تعریف smoke test برای مسیرهای حیاتی
- شناسایی نام‌های قدیمی باقی‌مانده و برنامهٔ مهاجرت امن

## یافتهٔ مهم فعلی

در branch فعلی، بعضی featureها هنوز به نام‌ها و کلیدهای قدیمی storage وابسته‌اند؛ نمونهٔ تأییدشده:

- alanRangStorageGetItem
- alanRangStorageSetItem
- alanrang_schema_migration_ledger_v1
- کلیدهای versioned مانند alanrang_pro

بنابراین تغییر نام سادهٔ متنی به AS کافی نیست. باید compatibility layer یا migration کنترل‌شده اضافه شود تا دادهٔ نصب‌های قبلی از بین نرود و wrapper اندروید با قرارداد جدید هماهنگ بماند.

## قرارداد موقت ذخیره‌سازی

الگوی مشاهده‌شده در ماژول‌ها:

1. اگر تابع native storage وجود داشته باشد، از آن استفاده می‌شود.
2. در غیر این صورت، fallback به localStorage انجام می‌شود.
3. داده‌ها غالباً به‌صورت JSON ذخیره می‌شوند.
4. بعضی ledgerها با محدودیت تعداد رکورد نگهداری می‌شوند.

تا پایان این فاز، هیچ کلید موجودی حذف یا rename نمی‌شود. کلیدهای جدید باید با نسخه و migration مشخص معرفی شوند.

## Native Bridge — موارد لازم برای استخراج

- نام object یا interface در WebView
- عملیات get/set/remove
- secure storage و رمزنگاری
- export/import فایل
- share و ارسال سند
- callbackهای موفقیت/خطا
- محدودیت حجم و encoding
- نسخهٔ قرارداد wrapper

سورس wrapper اندروید در branch فعلی موجود نیست؛ پس موارد بالا فعلاً باید از reference APK یا سورس wrapper جداگانه تأیید شوند.

## معیار عبور از فاز

فاز ۱ زمانی کامل است که:

- inventory state و storage در سند جداگانه ثبت شده باشد؛
- قرارداد bridge با wrapper واقعی تأیید شده باشد؛
- smoke testهای حیاتی اجرا و نتیجه ثبت شده باشند؛
- migration برای کلیدهای قدیمی تعریف شده باشد؛
- هیچ تغییر breaking در storage بدون نسخه‌بندی انجام نشده باشد.

## گام بعدی مستقیم

بعد از تکمیل inventory، یک compatibility adapter برای storage تعریف می‌کنیم و سپس به‌صورت مرحله‌ای route/state را از index.html جدا می‌کنیم. تا قبل از آن، تغییر نام کلیدهای قدیمی یا حذف فایل‌های versioned انجام نمی‌شود.
